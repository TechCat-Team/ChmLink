# 架构

[English](../architecture.md) | **简体中文**

本文介绍驱动和 SDK 的工作原理。SDK 的用法见 [sdk.md](sdk.md)。

## 组成部分

| 部分 | 位置 | 作用 |
|---|---|---|
| 驱动 | `driver/` | NDIS 6.60 miniport 驱动 `chmlink.sys`；一个驱动包支持两种网卡：`Root\ChmLink`（以太网）和 `Root\ChmLinkIP`（IP，`NdisMediumIP`） |
| SDK | `src/windows/` | `chmlink.dll`：会话、环形队列、网卡管理、内置的驱动包 |
| 共享代码 | `src/ring/`、`src/protocol/`、`src/packet/` | 环形队列、驱动与 SDK 之间的数据格式、数据包检查和辅助函数；可移植的 C 代码，同时编译进驱动和 SDK，并在 Windows 之外测试 |
| 工具 | `tools/` | `chmlink-device.exe`（以命令行形式提供 SDK 的网卡管理功能，静态链接）和 PowerShell 管理脚本 |

## 数据通路

一个会话就是一组共享内存环形队列：SDK 在应用进程中分配它们，并向驱动注册（`CHMLINK_IOCTL_REGISTER_RINGS`），
驱动锁定并映射这些内存：

- 一个**来自 Windows** 的环形队列：驱动在 `MiniportSendNetBufferLists` 中写入，应用读取；
- 最多四个**发往 Windows** 的环形队列：应用写入，驱动为每个环形队列开一个线程读取并交给协议栈。
  第一个随会话创建；SDK 为每个发送线程再加一个（`CHMLINK_IOCTL_ADD_INJECT_RING`）。

环形队列（`include/chmlink/ring.h`）的容量是 128 KiB 到 64 MiB 之间的 2 的幂（默认 4 MiB），
头部共 256 字节，有四个字段，各占一个缓存行：读取方的 `head`、写入方的 `tail`、读取方的 `wait` 标志，
以及驱动写入的 `state` 标志位（`CHMLINK_RING_STATE_RUNNING`、`CHMLINK_RING_STATE_CLOSED`）。
记录的格式是 `[u32 大小][12 字节卸载描述符][数据包]`，填充到 16 字节对齐，并且从不绕回：
末尾放不下的记录会放到队列开头，末尾剩下的空间标记为跳过。

通知机制沿用 Wintun 的做法：读取方发现队列为空时先短暂轮询，然后设置 `wait`，再检查一次，
之后等待事件；写入方只在 `wait` 被设置时才触发事件。两侧在休眠前都可以轮询：SDK 的等待函数（最多 64 µs），
以及驱动中发往 Windows 方向的线程（最多 100 µs，期间让出 CPU）。高包速和请求-响应式的流量下，下一个包通常会在这段时间内到达，
省去了每个包一次唤醒，并使 64 字节往返延迟减半左右（中位数约 15 µs，不轮询时约 35 µs）。

轮询是自适应的，因为在中等包速下轮询只会白白占用一个核心。两侧各自对"队列空了多久才来下一个包"做平滑估计
（没有数据的唤醒不计入），只在估计值低于 64 µs 时才轮询，否则立即休眠。请求-响应式的交互即使不轮询也低于这个阈值，
所以会重新打开轮询。这样在双向各每秒 10,000 个均匀间隔的包的情况下，一个会话只占 0.21 个核心，而不是一个或更多
（[performance.md](performance.md#资源占用)）。

**来自 Windows。** `MiniportSend` 在持有会话发送锁期间预留空间、复制数据包并发布，所以多个 CPU 上的发送方会轮流使用这把锁；
复制一个包的时间与前后的协议栈处理相比很短（四个发送方约每秒 127 万个包，与 Wintun 相当）。
遇到队列已满的包会被丢弃并计数（`tx_queue_drops`）。

**发往 Windows。** 环形队列的线程读取一批记录，构造直接指向已锁定队列内存的 NBL
（不复制，也不使用 `NDIS_RECEIVE_FLAGS_RESOURCES`），然后交给协议栈。每个环形队列跟踪自己的各个批次；
协议栈归还这些批次时，队列的 head 按顺序前移。暂停时会等待所有已交出的包归还。

**按流分发。** 协议栈在交出数据包的那个线程上处理它，所以单个交付线程最多只能用满一个核心
（在这里约每秒 65 万个包）。因此每个会话会为每个活动处理器启动一个工作线程，最多四个（单处理器时不启动）。
环形队列线程按 `chmlink_flow_hash` 把每个包放进一个桶。这个哈希由地址、协议和 TCP/UDP 端口计算，并跳过 IPv6 扩展头；
它是对称的，所以一条连接的两个方向落在同一个桶；分片不计端口，所以同一个包的所有分片落在同一个桶。
每一批中，线程自己交付其工作线程正空闲的最大的那个桶，这样单条流不需要转手；其余的桶交给各自的工作线程。
仍有包在处理中的桶总是交给它的工作线程，保证每条流的顺序。这正是物理网卡上 RSS 的做法。

**不可信的内存。** 驱动读取环形队列时，队列仍位于应用的内存中。驱动对每个索引和记录长度只读取一次，
对照队列进行校验，发现任何不一致就关闭会话。请求缓冲区（会话注册、卸载设置）在解析前由 I/O 管理器复制，
所有跨越内核边界的格式都使用显式的小端字段。数据包检查覆盖以太网最小长度、IP 头和长度字段的格式，
不检查校验和或协议语义。在以太网模式下，注入的包会遵守 Windows 的数据包过滤设置和组播列表。

## 设备契约

各应用可能附带自己的 `chmlink.dll`，而所有网卡共用一个驱动。两者通过带编号的契约达成一致
（`include/chmlink/version.h`）：

- 驱动支持从 `CHMLINK_DEVICE_VERSION_MIN` 到 `CHMLINK_DEVICE_VERSION` 的契约，并在查询结果中报告这两个值；
- SDK 在 `REGISTER_RINGS` 中给出自己的契约版本，并拒绝范围不包含它的驱动；
- 新契约只做增加：新的 IOCTL、能力标志位、写在保留字节或追加字节中且旧读取方会忽略的字段、需要会话主动启用的行为；
- 驱动支持的最旧契约只在主版本升级时提高。

因此 SDK 能与同一主版本下所有更新的驱动配合工作。创建网卡时会选择最新的驱动包（见
[sdk.md](sdk.md#安装哪个驱动)）。驱动包版本（`DriverVer`、`CHMLINK_VERSION_*`）与契约版本是两回事。

## 网卡类型

| | 以太网（`Root\ChmLink`） | IP（`Root\ChmLinkIP`） |
|---|---|---|
| 介质 | 802.3 | `NdisMediumIP` |
| 数据包 | 最长 MTU + 22 字节的以太网帧，允许 VLAN 标签，不含 FCS | 每个都是完整的 IPv4 或 IPv6 包（不支持 jumbogram） |
| MTU | 默认 1500，可为每块网卡设为 1280–9000 | 默认 1500，可为每块网卡设为 1280–65535 |
| 卸载 | LSOv2、TCP/UDP 校验和、RSC，按会话启用 | 无（Windows 不在 `NdisMediumIP` 上使用任务卸载） |
| 身份 | MAC（本地管理的单播地址） | 无 |

**卸载。** 由会话请求（`chmlink_set_offload`）；请求之前保持关闭，并且只有在这样的会话打开期间，Windows 才会看到这些能力。
之后数据包带有一个语义与 Linux `virtio_net_hdr` 相同的描述符。来自 Windows 的方向：最大 64 KiB 的 LSO 包，
以及校验和留待计算的包，其 IP 长度和 IPv4 头校验和由驱动修正。发往 Windows 的方向：标记为已校验的包跳过协议栈的检查，
合并后的 TCP 分段以 RSC 形式交出。在 IP 模式的网卡上，Windows 会忽略同样的卸载配置（在 build 26200 上实测），
所以 IP 网卡不提供卸载。

**大 MTU。** 在 IP 网卡上，MTU 相当于 LSO 和 RSC：协议栈以最大到 MTU 的包发送 TCP，也接受这么大的注入包。
默认保持 1500，使网卡的行为和普通网卡一样；设得更大时，由应用为更小 MTU 的路径切分数据包（`chmlink_ip_split`），
并可以在进入方向上合并它们（合并器）。

**软件 GRO。** `src/packet/gro.c` 把同一条流的连续 TCP 分段合并成一个大 IP 包或一个 RSC 帧。
合并条件：地址、端口、IP 字段、确认号和选项都相同；序号连续；标志只有 ACK 和 PSH；除最后一个外，每个分段都和第一个一样大。
IP 模式下，合并后的校验和由各分段的校验和字段推算，不读取负载；以太网模式下，由于 Windows 信任 RSC 数据，
除非调用方声明数据完好，否则会验证每个分段。看不到端口的 TCP（位于 IPv6 扩展头之后，或是 IPv4 分片）不会被合并；
为同一对主机暂存的分段会先于它发出，因此不会打乱任何一条流的顺序。

## 配置

每块网卡把身份信息存在自己的设备注册表键中：一个 64 字节、带版本号的值（配置版本 3），包含网卡 GUID、所有者 GUID、
模式、MAC（以太网）和 MTU，另外还有名称。驱动在启动时读取它，而不是根据接口索引生成 MAC，并拒绝在自己的实例之间出现重复的 MAC
或网卡 ID。身份在创建时确定；删除后重建的网卡会得到新的身份，Windows 接口 GUID 也可能随之改变。驱动把旧工具写入的版本 2 配置按
MTU 1500 读取。

## 生命周期与电源

暂停（配置变更、禁用）时，环形队列不再接收新包，驱动等待已交出的包归还并排空 I/O；会话保持打开，并报告
`CHMLINK_STATE_PAUSED`。系统睡眠报告为 `CHMLINK_STATE_LOW_POWER`，关机报告为 `CHMLINK_STATE_SHUTDOWN`，
移除报告为 `CHMLINK_STATE_REMOVING`；移除会结束会话。

暂停和关闭会话时，会不限时地等待协议栈归还所有从环形队列交出的包：这些包指向应用的内存，而 NDIS 不允许在协议栈仍持有时释放它们。
协议栈会很快归还；如果某个组件一直不归还，关闭（以及拥有该会话的进程的退出）会一直等到它放手为止。

## 安装模型

INF 有两种安装路径：build 25319 之前的系统把驱动复制到系统驱动目录（DIRID 12），更新的系统直接从驱动存储运行（DIRID 13）。
所有网卡共用 `chmlink` 服务，因此也共用一个驱动包；绝不会在创建一块网卡时顺带给另一块网卡安装驱动包。
